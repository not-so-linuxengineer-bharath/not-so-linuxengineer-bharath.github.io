Projects

Latprobe

Python · Linux · diagnostics
  • Most Linux performance tools make you already know which command shows what. Latprobe works the other way around: you tell it what you’re worried about (say, network jitter) and it runs the checks that matter for it.
  • 42 checks across 9 areas (CPU governor, C-states, SMT, NIC drops, IRQ affinity, NUMA, clocksource, hugepages). Each one comes back OK, WARN, or FAIL with the raw output and a suggested fix.
  • Safe to run from cron, with one heavier cyclictest check kept opt-in. Packaged as an RPM for RHEL, Amazon Linux, and Ubuntu.
  • The point is to go from “this box feels slow” to a short list of likely causes without poking at ten different files by hand.

HFT-style low-latency stack on AWS bare metal

Linux · DPDK · ENA · c6in.metal
  • People say you can’t get trading-grade low latency in the cloud without a Solarflare card, so I wanted to see how close you could get on plain AWS bare metal.
  • On a c6in.metal box: core isolation (isolcpus / nohz_full / rcu_nocbs), idle=poll with C-states capped, SMT siblings taken offline, IRQs moved off the app cores, and 1 GiB hugepages.
  • Got DPDK kernel bypass working through the ENA driver, with a busy-poll loop running on an isolated core.
  • Worst-case scheduling jitter went from 138 µs down to 7 µs, measured with open tools so anyone can repeat it.

udplat — UDP latency measurement tool

Python · networking · diagnostics
  • A small Python tool (no dependencies) that measures UDP round-trip time and reports p50, p99, p99.9 and max instead of just the average. It can output JSON and fail a threshold check, so it drops into monitoring.
  • Ping-pong style, one packet in flight at a time, with busy-poll and CPU-pinning options and packet-loss tracking.
  • I ran it between two c6in.metal boxes in the same placement group: p50 35.9 µs, p99 38.7 µs, no packet loss over 300,000 packets.
  • One thing that surprised me: busy-poll on its own was slightly worse than a normal blocking socket. It only helped once I pinned the thread to a core.

How I approach this work

  • I look at p99 and the max, not just the average. The slow one-in-ten-thousand is usually what people are actually complaining about.
  • A lot of “random” slowness comes down to CPU power states or processes ending up on the wrong cores, so I check those early.
  • I read the current setting before changing it. Often it’s already fine and the real problem is somewhere else.
  • If I can’t show a before-and-after measurement, I don’t really trust the fix.
