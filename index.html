About

I’m Bharath, a cloud and low-latency systems engineer. Most of my work lives below the application: CPU isolation, C-states, NUMA placement, interrupt handling, and the Linux network path. The interesting problems down here rarely show up as errors. They show up as a graph that’s fine on average and, occasionally and expensively, isn’t.

My approach is measure first, theorise second. Form a hypothesis, instrument the system, read the evidence, then say what’s happening, and write it up so the next person doesn’t have to rediscover it.

HFT-style low-latency stack on AWS bare metal

Linux · DPDK · ENA · c6in.metal

The number I’m proud of

138 µs→7 µs
Worst-case scheduling jitter on c6in.metal (cyclictest -p99, 840k samples). The average was 1 µs the whole time, the win is the tail, and in low-latency work the tail is the point.

Things I believe about performance

  • The average is a comforting lie. Measure p99.9 and max, or you’re measuring nothing.
  • Deep C-states are the number-one source of microsecond jitter nobody looks at.
  • A perfectly pinned thread reading remote-node memory still pays the NUMA tax.
  • Don’t tune from theory. Read the current value first, change one thing, then re-measure.
  • If a result has no reproducible measurement behind it, it’s an opinion, not a finding.
