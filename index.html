about

I’m Bharath. I spend my time in the unglamorous middle of the stack, where the kernel meets the hardware: CPU power states, NUMA, IRQ affinity, the network data path. The bugs down here rarely show up as errors. They show up as a graph that’s fine on average and occasionally, expensively, isn’t.

My favourite kind of work is turning “it’s slow sometimes” into a number, a cause, and a fix you can reproduce. Form a hypothesis, instrument the box, read the evidence, and only then say what’s happening. Then write it down so the next person doesn’t have to rediscover it.

The handle is a joke, mostly. I like Linux more than is strictly healthy.

latprobe [private]

Python · Linux · low-latency diagnostics

A symptom-driven latency & jitter diagnostic tool. Instead of making you remember that column 2 of /proc/net/softnet_stat counts softirq drops, you tell it “I care about network jitter” and it runs the right battery: 42 checks across 9 profiles (CPU governor, C-states, SMT, NIC drops, IRQ affinity, NUMA, clocksource, hugepages), each scored OK / WARN / FAIL with the raw evidence and a concrete fix. things I believe about performance

  • The average is a comforting lie. Measure p99.9 and max, or you’re measuring nothing.
  • Deep C-states are the number one source of microsecond jitter nobody looks at.
  • A perfectly pinned thread reading remote-node memory still pays the NUMA tax.
  • Don’t tune from theory. Read the current value first, then change one thing, then re-measure.
  • If a result has no reproducible measurement behind it, it’s an opinion, not a finding.
