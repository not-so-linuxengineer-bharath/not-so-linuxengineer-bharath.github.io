Building an HFT-style low-latency stack on AWS bare metal

All numbers below were measured on a real instance with open-source tools and are reproducible. Sources are public AWS and DPDK docs.

The claim I wanted to test

There’s a persistent belief that you can’t do high-frequency-trading-grade low latency in the cloud, because you can’t run a Solarflare/Onload kernel-bypass NIC. I wanted to see how far the standard HFT Linux playbook gets you on an AWS bare-metal instance, and measure it honestly.

The box

  • c6in.metal: 2× Intel Xeon 8375C (Ice Lake), 128 vCPU, 256 GiB, 200 Gbps.
  • Amazon Linux 2023, kernel 6.1.
  • A network-optimized metal instance, because metal gives you real VFIO/PCI passthrough (needed for DPDK) and the n line has the highest packet rate.

The headline result

Worst-case scheduling latency measured with cyclictest (-p 99, 14 threads on the app cores, 60 s, 840,000 samples), before and after tuning:

AverageWorst-case max (the jitter tail)
Before (stock AL2023)1 µs138 µs
After (full tuning)1 µs7 µs

The average never moved, and that’s the most interesting finding. Amazon Linux 2023 on metal already ships with the performance CPU governor and a TSC clocksource, so steady-state latency is already excellent out of the box. The entire win was in the tail: collapsing the occasional 138 µs spike down to a bounded 7 µs.

(If “tail” is new: it’s the slow end of the latency distribution, the p99.9 and the max, the worst cases you hit occasionally rather than the typical average. You never feel the average; you feel the worst case. That’s why, in trading, the tail is the only number that matters.)

What actually moved the tail

Everything here is standard Linux, documented publicly, no proprietary tooling:

  1. Core isolation via kernel cmdline: isolcpus, nohz_full, rcu_nocbs on the application cores, removing them from the scheduler, the timer tick, and RCU callback processing.
  2. C-state control: idle=poll and capping the max C-state at 1. Deep C-states are the single biggest source of microsecond wake-up jitter.
  3. SMT isolation: I took the Hyper-Thread siblings of the app cores offline so a sibling can’t contend for shared execution units (done per-core, so housekeeping cores keep their threads).
  4. IRQ steering: moved every interrupt onto a pair of housekeeping cores and stopped irqbalance, so nothing fires on the app cores.
  5. 1 GiB hugepages to cut TLB pressure.
  6. mitigations=off, a real latency win, but a security trade-off. Only on an isolated, single-tenant box.

Kernel bypass without Solarflare

This is the part people don’t expect. AWS’s NIC, the Elastic Network Adapter (ENA), has a native DPDK Poll Mode Driver, and it supports a Low Latency Queue (LLQ) mode. On a metal instance you get real vfio-pci passthrough, so you can do genuine userspace kernel bypass.

“The ENA PMD is a DPDK poll-mode driver for the Amazon Elastic Network Adapter (ENA) family… The PMD attempts to enable the LLQ (Low Latency Queue) whenever it’s possible.” Source: DPDK ENA Poll Mode Driver docs

I attached a second ENI, bound it to vfio-pci, and ran a busy-poll, run-to-completion loop entirely in userspace on an isolated core. The ENA Poll Mode Driver came up, mapped the device, and the loop polled the NIC with zero syscalls on the hot path. That’s the AWS equivalent of Onload. It’s just called ENA + DPDK.

And for timestamps: the Amazon Time Sync Service now exposes a PTP Hardware Clock with nanosecond-precision hardware packet timestamps, so you don’t need to run your own grandmaster clock.

“The Amazon Time Sync Service now supports nanosecond-precision hardware packet timestamping on supported Amazon EC2 instances.” Source: AWS What’s New, June 2025

What you give up vs. a colo cage (being honest)

  • No BIOS access. Nitro abstracts the firmware, so you can’t disable C-states or prefetchers in BIOS. Everything is kernel cmdline and /sys.
  • No Solarflare/Onload. You use the ENA DPDK driver instead. It genuinely is kernel bypass, but it’s a different ecosystem.
  • Nitro-managed turbo/P-states, which are less granular than raw hardware.

Honest scope of the numbers

These are single-host scheduling-latency numbers (cyclictest), which isolate the OS jitter, exactly the thing tuning fixes. They are not end-to-end wire latency. Measuring true tick-to-trade latency needs a second instance as a packet generator in a cluster placement group. That’s the follow-up.

Everything was measured with cyclictest, perf, and ethtool, all open tools, so you can reproduce every number.

Takeaway

The cloud isn’t a colo cage, but the gap is smaller than the folklore suggests. On AWS bare metal, standard Linux tuning took worst-case jitter from 138 µs to 7 µs, and the ENA DPDK driver gives you real kernel bypass. For a large class of latency-sensitive workloads, that’s more than enough, and you skip the data-center contract.
